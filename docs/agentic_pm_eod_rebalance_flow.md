# Agentic PM EOD Rebalance Flow

Status: design note for the current long-only, Tastytrade-routed PM loop.

## What `current` must mean

For any live or sandbox EOD decision, `current` means the account's actual broker holdings, not the previous canonical shadow target.

Correct launch behavior:

1. Read Tastytrade account equity and equity positions.
2. Convert each equity position to a fraction of net liquidation value.
3. If the account has no equity positions, treat current weights as an empty/zero book.
4. Only fall back to the previous canonical target when the operator explicitly chooses a shadow/backtest comparison mode.

Using a previous canonical target as `current` while the broker account is empty makes turnover, current overlap, hold locks, and PM eligibility stale. It can cause the Agentic PM to prefer `hold_current` even though there is nothing in the account to hold.

## Current architecture

The Agentic PM does not invent security weights or submit orders directly. The intended chain is:

```text
market panel
  -> deterministic strategy + chimera candidate board
  -> agent/human chooses one eligible candidate_id
  -> review guard + receipt + audit
  -> activation copies the chosen candidate's weights into canonical svyable_nasdaq_lo artifacts
  -> rebalance planner diffs canonical target weights against actual Tastytrade positions
  -> preflight
  -> sandbox submission, or production procedure after separate explicit live gate
```

The effective EOD output is therefore two artifacts:

1. **Today's target weights**: the activated candidate's `weights_today.csv`.
2. **Today's rebalance instructions**: broker order intents generated by diffing those target weights against actual Tastytrade positions.

## Strategy versus chimera versus transition

A strategy is a complete deterministic recipe.

A chimera is a deterministic portfolio-level blend of strategy outputs, for example 60% defensive + 40% trend. It is still evaluated as a candidate and can be activated like a normal strategy.

A transition candidate is similar in spirit, but it blends the actual current broker book with a target candidate, for example:

```text
transition_25__q23_alpha_beta = 75% current actual book + 25% q23_alpha_beta target
transition_50__q23_alpha_beta = 50% current actual book + 50% q23_alpha_beta target
transition_100__q23_alpha_beta = 100% q23_alpha_beta target
```

Transition candidates should be treated as execution overlays, not new alpha strategies. They are useful when the best alpha candidate is directionally right but too expensive or too large to enter in one step.

## Long-only documentation correction

The implemented constructor is currently long-only. It selects the highest-scoring seats, projects positive weights onto a capped simplex, smooths versus yesterday, and applies no-trade bands. It does not currently construct a separate short sleeve.

Docs and dashboards should describe this as:

```text
Panel -> factors -> sleeve/meta weighting -> composite score -> long-only capped simplex portfolio -> risk budget -> target weights
```

If long/short returns later, that should be a separate implementation milestone with tests, not implied by the current docs.

## Required improvements

1. Add an explicit current-position mode to the daily runner and dashboard:
   - `broker_actual` default for Tastytrade EOD.
   - `zero` for account launch / no-position sandbox tests.
   - `canonical_target` only for shadow comparison.

2. When current source is `broker_actual` or `zero` and the current weights are empty, treat the selection state as cash. Do not apply stale `selected_strategy_id` hold locks.

3. Permit full initial deployment from cash by bypassing the max-turnover eligibility ceiling only for launch-from-cash runs. Keep alpha, kill-switch, stale-input, and review gates.

4. Score `hold_current` like a real candidate. It should inherit risk penalty and artifact health from the current strategy when a current strategy exists, instead of receiving zero risk/cost penalty by construction.

5. Keep the agent's decision surface candidate-based. The agent should select a strategy, chimera, or generated transition candidate; activated weights and rebalance transactions should remain deterministic, auditable artifacts.

6. Keep production submission guarded. Sandbox can have one-button preflight + submit. Production should require a separate live enable flag and typed account confirmation before any bulk submission path is enabled.

## Desired dashboard flow

1. Launch dashboard via the batch file.
2. Refresh broker snapshot and show whether actual current positions are zero.
3. Run full-frontier candidate evaluation using broker/zero current positions.
4. Agentic PM reviews strategies, chimeras, and transition candidates.
5. Agent writes one guarded candidate decision.
6. Review chain passes.
7. Human approves activation.
8. Dashboard builds today's rebalance plan from activated target weights versus actual Tastytrade positions.
9. Dashboard preflights all orders.
10. Sandbox button submits today's rebalance instructions through the Tastytrade API.
11. Ledger records orders, fills, reconciliation, and drift.
